# 목적과 인계 맥락

## 확정된 요구사항

담당자의 DB 이전·컷오버와 에이전트 리허설 네임스페이스 관련 태스크를 실제 AWS·RKE2에서 검증한다. 결과 조회에 더해 웹에서 실제 테스트를 트리거해야 한다. 현재 클러스터가 선택한 테스트를 수행할 준비가 되었는지 확인하고, 실제로 실행되는 DB 전환과 격리 Job의 상태를 시각화한다. 이후 고도화 후보를 안전하게 시도하는 테스트베드로 발전시킨다.

별도 조직 저장소에서 개발하고 사용자가 Orca 프로젝트로 추가한다. platform을 규칙·계약·기본 설정의 SOT로 유지하며 작업물을 플랫폼으로 옮길 수 있게 구성한다. 별도 저장소의 main은 기존 플랫폼 main과 다른 브랜치다. 레포 분리는 실환경 자원 격리를 대신하지 않는다.

## 담당 범위와 연결

주요 범위는 T3·T12·T15·T20·T25·T42이며 T26 평가는 후속 확장이다. 공식 담당은 플랫폼 이슈 Assignees를 작업 시작 시 확인한다. DB 복제 기반 T8·무결성 T13·부하 T18·목적지 T30·런타임 T38·API T10·AI 도구 T11은 기존 생산자와 연결한다. T21 콘솔 변경이 필요하면 담당자와 범위를 합의한다. 테스트베드에서 별도 화면을 만드는 것과 플랫폼 T21을 수정하는 것은 구분한다.

## 초기 확인 기록의 범위

2026-11-06 확인한 플랫폼 이슈에서 T25의 실제 첫 컷오버·복귀와 반복 측정은 미완료였다. T15는 RKE2 격리 시험 완료, OpenBao 자격 파일을 통한 코드 수정 템플릿 시험 미완료로 표시됐다. T42는 호출 계약 확인 후 실제 모델·broker·러너 경로 실측 등이 남아 있었다. 이는 당시 이슈 기록이며 현재 클러스터의 실행 가능 판정이 아니다. 시작 시 이슈와 실제 배포 SHA·접속·권한을 다시 확인한다.

플랫폼 문서와 이슈 사이에는 갱신 시차가 있을 수 있다. 로컬 README나 그래프의 구현 존재만으로 배포·실환경 인수를 완료로 간주하지 않는다. 초기화 시 실환경 테스트는 실행하지 않았다.

## 다음 시작점

1. `config/upstream.json`과 플랫폼 최신 규칙·계약·담당 이슈를 확인한다.
2. 읽기 계정으로 AWS·RKE2 접근과 기존 API·실행기의 배포 버전을 확인한다. 실제 주소·자격은 저장소에 기록하지 않는다.
3. 전용 테스트 DB·복제 경로·리허설 namespace·쓰기 및 정리 권한의 제공 여부를 파악한다. 없는 자원은 미확인으로 남긴다.
4. 플랫폼의 웹·서버 도구를 조사해 최소 앱 구조를 정한 뒤 준비 상태 조회부터 구현한다.

아직 정하지 않은 항목은 프런트엔드/서버 스택, 호스팅, 실제 환경 별칭, 로그인 공급자, 자격 전달 방식, 테스트 자원 할당이다. 모두 플랫폼의 현 구성을 우선 재사용하며 이 초기 문서를 확정 설계로 해석하지 않는다.
